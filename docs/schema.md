# Catalog schema

Source of truth is `apps/expo-api/migrations/000001_init.up.sql` (the
curated tag rows and reserved usernames are in
`000002_seed_initial_data.up.sql`); this file
summarises shapes and invariants. Update it with any migration. Tooling:
[database.md](database.md).

## Principles

- Books, blueprints and planners are first-class rows; nesting is a shape-only tree.
- Revisions are immutable; editing an entry adds a revision.
- `entries.owner_user_id` is nullable forever; no placeholder users.
- Execution state is split by owner: API tables hold dispatch intents and imported results; `runner_*` tables are the runner's (see below).

## Tables

**`users`**: `id` short id, `username` unique, CHECK `^[A-Za-z0-9_-]{3,32}$`, also unique on `lower(username)`; `created_at`; `status` (the profile's status line: at most 140 characters, one line, default empty; cleared by staff and at the account's deletion); `deleted_at` (account deleted by its owner or staff: every `users.sql` lookup skips it, so the profile stops working, and its sessions and sign-in methods (`auth_identities`, `user_passkeys`) are deleted with it, so its provider accounts may sign up anew at once unless an active ban leaves `ban_holds`; the row keeps its username until the API's daily sweep hard-deletes it with its entries 7 days after the deletion, or the `deleted_accounts` cleanup does sooner, once it owns no entry). `recovery_code_hash` (bytea, 32 bytes, nullable): SHA-256 (domain-prefixed) of the account's recovery code, 128 random bits shown once at sign-up (`internal/accounts/recoverycode.go`); the code is never stored. `POST /api/v1/auth/recover` swaps it for a new hash atomically (`UPDATE ... WHERE recovery_code_hash = $used`, so concurrent uses succeed once); set to null at the soft delete with the sign-in methods. No email and no password: an account signs in with its identities or passkeys below, and always keeps at least one (`internal/accounts`, under a row lock); a recovery code is the way back after losing them all.

**`reserved_usernames`**: usernames nobody may sign up with (staff words, site routes, the brand). `name` pk, the normalized form `translate(lower(username), '_-', '')` (CHECK `^[a-z0-9]{1,32}$`), so a username matches ignoring case, `_` and `-` (`Ad_min` is `admin`); `reason` (free text: staff, technical, placeholder, site route, brand); `created_at`. Seeded in `000002_seed_initial_data`; checked with the existing usernames by `UsernameUnavailable` (both sign-up paths and the provider name suggestion). Accounts that already have such a name keep it. Staff add and remove names in the console ([admin](admin.md#reserved-usernames)).

**`auth_identities`**: an account at a sign-in provider. PK (`provider`, `provider_user_id`): `provider` lowercase letters/digits (github, discord, steam, google), `provider_user_id` the provider's own stable id (1-255 chars; never an email or a name); `user_id` (cascade); UNIQUE (`user_id`, `provider`): one account per provider per user; `created_at`, `last_used_at`. Deleted with its account at the soft delete.

**`user_passkeys`**: a WebAuthn passkey. `id` short id; `user_id` (cascade; the passkey's user handle is this id); `credential_id` bytea UNIQUE across all users (the sign-in lookup); `credential` jsonb (go-webauthn's `Credential`: public key, flags, sign count, transports, AAGUID), rewritten after each sign-in; `created_at`, `last_used_at`.

**`user_sessions`**: a signed-in browser or API client (`internal/sessions`). `id` short id (the session JWT's `sid` claim); `user_id` (cascade); `created_at`; `last_used_at` (refreshed by a request only when older than 5 minutes, so most requests write nothing); `expires_at` (sign-in + 7 days, like the cookie; CHECK after `created_at`); `auth_time` (when the person last completed a sign-in ceremony on this session: the sign-in, or a later "confirm it's you"; sensitive account changes need it within 10 minutes, [api.md](api.md#sessions-and-sign-in)). Dates only: no IP address, no user agent. Every authenticated request reads its row (live, account not deleted); deleting rows signs devices out: logout (this one), "log out everywhere", removing a sign-in method (all but the current one), staff force logout and account deletion (all). The API's hourly sweep deletes expired rows. There is no `users.token_version`: these deletes cover every revocation.

**`entries`**: `id` short id (the public id), `title`, `description` (uploader-authored, independent of node labels), `owner_user_id` nullable, `edit_token_hash` unique nullable (hex SHA-256 of the anonymous edit token; the token itself is never stored), `visibility` `public|unlisted|private` (unlisted and private require an owner; unlisted is viewable by link but never listed or indexed, see [api.md](api.md)), `current_revision_id`, `created_at`, `updated_at`, `deleted_at`, `expires_at` (nullable; when the entry ends: missing once expired, then removed by the API's minute sweep. Always set on a quick preview; an upload may choose 1, 7, 14 or 30 days, null by default), `comment_seq` (the last comment number handed out; never reused), `source_url` (nullable; the canonical https link an imported blueprint came from, `CHECK` https and at most 2000 characters, set only at upload from an [import](api.md#import-from-other-sites); shown as "Imported from"), `spoiler` (bool, default false; spoiler/NSFW, set by whoever may edit the entry on upload, publish or the details form: clients hide its previews until a click, search can leave it out, see [frontend.md](frontend.md#feature-notes)), `quick_preview` (bool; a quick preview: never indexed or listed, read-only, hard-deleted by the sweep once expired or at once when its preview or analysis fails for good; publishing clears it and sets the expiry the publisher chose; `CHECK (NOT quick_preview OR expires_at IS NOT NULL)`). An expired upload is soft-deleted by the sweep with a search delete queued (`ExpireEntries`), like a delete. Delete is soft; every read filters on `entry_live(entries)` (viewer reads go through `catalog.entryAccess.Viewable`, edits through `Editable` with the row locked), and children stay so `entry_search_jobs` can still issue the index delete. Metadata edits and tag changes never create revisions.

**Entry lifecycle functions** (SQL, inlined by the planner; Go twins in `catalog/lifecycle.go`, kept in agreement by `TestLifecycleRulesMatchSQL`): `entry_live(entries)` not deleted and not expired; `entry_visible_to(entries, viewer)` private entries only to their owner (viewer null when signed out); `entry_listed(entries)` live, public, not a quick preview, with a revision: what search indexes, public profiles list, and the only entries that take comments; `entry_lasting(entries)` live and not a quick preview: the entries that get cards and stay in favorites, collections, owner listings and view counts (no Go twin: no Go code decides it; the test checks it against `entry_live`). `ban_active(user_bans)` neither revoked nor expired (Go twin `catalog.BanActive`, `TestBanActiveMatchesSQL`). Queries call these instead of spelling the columns out.

**`revisions`**: `id`, `entry_id`, `version_number` (unique per entry, from 1), `original_string` (exact submitted bytes), `tree` jsonb, `game_version` (exporting game version read from the exchange string, e.g. `2.0.15`, may be empty), `compat_21` (`''`, `compatible` or `incompatible`: the Factorio 2.1 verdict of a submission made before 2.1, `blueprint.Compat21`; entry cards and search results carry it as `compat_21` and show the version badge), `note` (the uploader's optional change note, trimmed, at most 280 characters, `''` for none; shown in the revision list and timeline and in the user's feed, never on the profile), `created_at`. Never updated.

**`entry_aliases`**: `entry_id` (primary key, cascade), `user_id` (the owner it was set for, cascade), `slug` (`CHECK` lowercase letters, digits and hyphens, 3 to 60, starting and ending alphanumeric; the reserved words and id-shaped slugs are refused in `catalog/alias.go`), unique `(user_id, slug)`. The [vanity alias](api.md#read-routes-worth-knowing) of an entry: `/@{username}/{slug}`. Changing it replaces the row (no history). A slug whose entry is no longer live is taken over by the next user of it in `SetEntryAlias`'s transaction (`DeleteStaleAlias`), so deleting or expiring an entry needs no cleanup.

**`books`**: `id`, `revision_id`, `label`, `description`, `icons` (rich-text, e.g. `[item=iron-plate]`), `active_index` nullable. Never stores an exchange string.

**`blueprints`** (renderable leaves): `id`, `revision_id`, `label`, `description`, `icons`, `exchange_string` (self-contained, independently renderable), `exchange_sha256` (its SHA-256, indexed: finds leaves with the same string for [result reuse](architecture.md#result-reuse); matches are confirmed on the string), `entity_count`, `position` (leaf ordinal in depth-first tree order within the revision; the cover is the lowest-position leaf that has a preview), `compat_21` (the leaf's [2.1 compatibility](architecture.md#21-compatibility); `''`, `compatible` or `incompatible`), `snap_to_grid` jsonb (`blueprint.SnapToGrid`: `width`, `height`, `absolute`, `offset_x`, `offset_y`; null when the blueprint has no grid). Book and root strings are not stored; they are re-encoded on demand from leaves and planners.

**`planners`** (upgrade and deconstruction planners): `id`, `revision_id`, `kind` (`upgrade_planner|deconstruction_planner`), `label`, `description`, `icons`, `exchange_string` (self-contained), `settings` jsonb (the stored shape: `blueprint.UpgradeSettings` `{mappers: [{index, from?, to?}]}` or `blueprint.DeconstructionSettings` `{entity_filter_mode, entity_filters, trees_and_rocks_only, tile_filter_mode, tile_filters, tile_selection_mode}`; a filter is `{index, type?, name, quality?, comparator?, module_limit?}`, no quality meaning any). Planners are never rendered or analysed: no position, jobs, stats or previews, and they do not count as leaves.

**`blueprint_stats`**: one row per blueprint (`blueprint_id` unique). Structural: `entities` jsonb (`[{name, count}]`, with quality), `recipes` jsonb, `mods` jsonb (a `mods.Detection` from those names) and `mods_version` (the embedded name table it was made against; `''` before detection; the API re-detects older versions at startup). Production, independent of the structural fields: `production` jsonb, `production_schema_version` (>0, currently 1), `production_state` `complete|partial` (named to avoid confusion with item quality), `production_stale` (refresh failed but old snapshot kept), `production_calculated_at`. Snapshots keep schema version and inherited content set, not calculator-build provenance. No automatic backfill after analyzer upgrades.

Books, blueprints and `blueprint_stats` rows have no `created_at`: they are written in the same transaction as their revision, so its `created_at` is theirs.

**`previews`**: one row per blueprint, inserted only after a successful render and once both its files are in the API's file storage: `source_sha256` (SHA-256 of the runner's PNG, lowercase hex), `width`, `height` (of the full image). `source_sha256` names the files (`previews/<sha[:2]>/<sha>.webp`, the full image, and `<sha>.thumb.webp`, the thumbnail; a preview within 800x800 px has only the thumbnail, derived from `width`/`height`) and is their ETag, so identical renders share files (indexed). Media type (always WebP), file sizes and thumbnail dimensions are derived, not stored ([architecture](architecture.md#preview-files)).

**`preview_files`**: `source_sha256` pk, `thumbnail_bytes`, `full_bytes` (null: no full file, because the preview is small or the [storage budget](architecture.md#preview-files) evicted it), `stored_at` (files last written; the eviction order, with a partial index over rows that have a full file). One row per source whose files are stored, written by `preview.Files` (`RecordPreviewFiles`) and deleted with the files by the sweep. Leaf reads join it for `preview.full_available`.

**`preview_file_deletions`**: `source_sha256` pk, `created_at`. Sources whose files may have lost their last reference: the `previews_queue_file_deletion` trigger adds one for every deleted `previews` row (cascades from hard-deleted entries included), `previews_queue_replaced_file_deletion` one for a row a re-render pointed at a different source, and an import adds its source when no row took its files (`catalog.StorePreview`, in the same transaction as the attempted insert). The minute sweep deletes the files of a source no `previews` row references, then the row.

**`phase_jobs`**: API dispatch intent per leaf and phase (`blueprint_id` + `phase` `preview|analysis` pk, `runner_job_id`, `state` `pending|failed`, `retry_count`, `available_at`, `failure_code`, `failure_detail`, timestamps), and its [render queue](architecture.md#render-queue) place: `queue_key` (`u:<user id>`, `ip:<hex HMAC of the address>`, `staff`, `system`; the per-uploader cap counts pending rows by it), `order_at` (the dispatcher sends the lowest first), `runner_settled` (the runner job finished; it no longer holds a dispatch window slot while its results are imported). Deleted when the `previews` row / current production snapshot is stored; presence means outstanding or terminally failed. A job row next to a stored result is a re-run ([architecture](architecture.md#preview-files); today a re-render of an evicted full file). Readiness is derived from the `leaf_progress` view (one row per blueprint: has preview, has production, each job's state and failure code) by `progress.LeafOf`: an open job is pending (also over a stored result), else a stored result is ready, else a job failed for good is failed, else pending.

**`entry_search_jobs`**: `entry_id` pk, `action` `index|delete`, `state`, `retry_count`, `available_at`, failure fields. One row per entry, a new enqueue overwrites the action; deleted after a successful sync. See [search.md](search.md).

**`runner_jobs`, `runner_artifacts`**: runner-owned queue and temporary artifact records in the runner's own database, defined in `apps/expo-render-worker/migrations/`. They are not part of the catalog database.

**`tag_groups`**, **`tags`**, **`entry_tags`**: `tag_groups(id, slug unique, display_name, position)` and `tags(id, group_id, slug unique, display_name, icon, position)` (`icon`: a rich-text icon token such as `[item=splitter]`, `''` for none; shown on tag chips) seeded with a curated set in `000002_seed_initial_data` (12 groups) and edited by staff in the console ([admin](admin.md#tags)); ids derive from the slug (`left(md5('tag:' || slug), 12)`, `'tag-group:'` for groups), and slugs never change; every tag has exactly one group and users attach existing tags only. A group without tags is left out of `GET /api/v1/tags`. Deleting a tag queues its entries' search reindex and cascades `entry_tags` and its rules. Facts derivable from the blueprint or analysis (version, mods, planet, space platform, belt tier, science produced) are search facets, not tags. `entry_tags(entry_id, tag_id)` pk both.

**`tag_suggestion_rules`**: pk `(tag_id, kind, name)`, `kind` `entity|recipe|quality` (`quality`: `name` is `uncommon`..`legendary`, counted over every entity of that quality), `min_count` (>= 1), nullable `max_count` (>= `min_count`; null = no upper bound), `points` (>= 1, default 1). Seeded in `000002_seed_initial_data` (a mistyped tag slug fails it), edited in the console (a name must be one the mod name table knows); loaded at API startup and reloaded after each console edit to score [tag suggestions](architecture.md#blueprint-string-tools-and-tag-suggestions). Names are prototype names of the pinned game.

**`entry_view_counts`**: `entry_id` pk (cascades with the entry), `views` (all-time page views, added by the API's periodic flush; see [architecture](architecture.md#page-views)), `indexed_views` (the count last sent to the search index; rows where it differs from `views` are partially indexed: `idx_entry_view_counts_unindexed`). Kept off `entries` so the frequent updates do not touch entry rows.

**`entry_view_days`**: `(day, entry_id)` pk (cascades with the entry), `views` (page views that UTC day, added by the same flush). Read by trending; rows of earlier months are pruned daily.

**`user_social_links`**: pk `(user_id, platform)` (cascade), `platform` one of `youtube`, `twitch`, `github`, `reddit`, `bluesky`, `steam`, `x`, `handle` (1-253 chars; the name only, the API builds the link and checks the name per site). Deleted at the account's deletion. **`user_pinned_entries`**: pk `(user_id, entry_id)` (both cascade), `position`, `pinned_at`; at most 6 per user (API, under the user row lock), only the user's own listed entries; a pin whose entry is no longer listed is skipped on read and pruned at the user's next pin change. Deleted at the account's deletion.

**`favorites`**: pk `(user_id, entry_id)`, `created_at`. **`collections`**: `id`, `user_id`, `name` (1-100 chars), `description` (<= 2000), `visibility` (default private), `created_at`. **`collection_entries`**: pk `(collection_id, entry_id)`, `position`, `added_at`.

**`comments`**: `id`, `entry_id` (cascade), `number` (public `#N`, unique per entry, from `entries.comment_seq` under the entry row lock), `author_user_id`, `revision_number` (live revision when posted), `body` (Markdown, <= 4000), `created_at`, `edited_at`, `deleted_at` + `deleted_by` (`author|owner|admin|account`, `account`: the author deleted their account; a removed comment is a tombstone with an empty body). One flat thread per entry; only public, non-quick-preview entries have one, and leaving public deletes it ([api](api.md#comments-reports-notes)).

**`comment_reports`**: pk `(comment_id, reporter_user_id)`, `reason` (`spam|abuse|off_topic|other`), `note` (<= 500), `body_snapshot` (the body when reported; comments can be edited), `created_at`, `resolved_at`/`resolved_by` (the staff member's console username). Open reports are indexed for the admin panel.

**`blueprint_notes`**: `id`, `blueprint_id` (cascade), `x`/`y` (fractions 0..1 of the preview image, so a pin follows the image at any size), `body` (1-500 characters, Factorio rich text), `created_at`, `edited_at`. Indexed `(blueprint_id, created_at, id)`: the pin number is the note's rank in that order (`row_number()` in the list query), not a stored column. Written by the entry's editor on a live-revision leaf only (`catalog/notes.go`); the 20-per-leaf cap is checked under the entry row lock.

**`entry_reports`**: `id`, `entry_id` (cascade), `reporter_user_id` (signed-in reporter, cascade) or `reporter_ip_hash` (an anonymous reporter's HMAC-SHA256 IP hash, as in `ip_bans`; never both, and cleared when the report is resolved), `reason` (`stolen|offensive|spam|misleading|other`), `note` (<= 1000), `revision_number` (the revision viewed), `title_snapshot`/`description_snapshot` (the entry as reported), `created_at`, `resolved_at`/`resolved_by` (the staff member's console username). At most one open report per reporter per entry (partial unique indexes); open reports are indexed for the admin panel. Reports never hide an entry by themselves ([api](api.md#comments-reports-notes)).

**`problem_reports`**: the bug button's reports ([api](api.md#comments-reports-notes)): `id`, `reporter_user_id` (cascade) or `reporter_ip_hash` (never both; cleared when resolved), `body` (1-4000), `email` (opt-in contact address, cleared when resolved or after 30 days open), `page_path` (no query), `entry_id`/`blueprint_id` (no foreign keys: the report outlives them), `context` (jsonb object of short strings), `user_agent` (<= 500), `created_at`, `status` (`open|fixed|wont_fix|duplicate|spam`), `staff_note` (<= 1000), `resolved_at`/`resolved_by`. Open iff unresolved; a resolved report holds no email or IP hash. Deleted 7 days after it was resolved (hourly sweep).

**`user_bans`**: `id`, `user_id`, `actions` text[] (`comment`, `upload`, `report`), `reason_code` (`spam|abuse|illegal_content|other`), `note`, `banned_by`, `created_at`, `expires_at` (null: permanent), `revoked_at`/`revoked_by`. Kept as history; active = not revoked and not expired. Created, changed and revoked by staff; `banned_by`/`revoked_by` are console (Cloudflare Access) emails.

**`ip_bans`**: pk `(ip_hash, action)`, `reason_code`, `created_at`, `expires_at` (required). Short IP bans, independent of `user_bans`: `ip_hash` is the HMAC-SHA256 (`API_IP_HASH_SECRET`) of the client IP (IPv6 by /64), never the IP. Written only when a banned account tries a blocked action (one row per action of its ban, for `API_IP_BAN_DURATION`, never past the user ban's end; a repeat extends it). Staff also ban an anonymous entry reporter's hash for `report`, and may lift any row early. Expired rows are pruned hourly. The only other IP data is an open anonymous entry report's `reporter_ip_hash`.

**`ban_holds`**: pk `hash` (32 bytes), `kind` (`username|identity`), `created_at`, `expires_at`. What a deleted account with an active ban leaves behind, since its `user_bans` rows go with the account: HMAC-SHA256 hashes (`internal/banhold`, key derived from `API_IP_HASH_SECRET`) of its username, normalized like `reserved_usernames`, and of each provider identity (provider + provider user id); never the name or id. Written at the soft delete, until the latest active ban ends (a permanent ban: one year); a repeat extends. Sign-up refuses a held username (`UsernameUnavailable`), sign-in, sign-up and linking refuse a held identity (`accounts.ErrIdentityHeld`). A passkey-only account holds only its username. Expired rows are pruned hourly with the IP bans.

**`global_settings`**: the emergency switches and other runtime settings ([admin.md](admin.md#settings)). `key` (primary key), `value` (text: `true`/`false`, a number or a string), `updated_at`, `updated_by` (console username). Which keys exist, their types and defaults are defined in code (`internal/settings`): a missing row means the default, an unknown key is ignored, so adding a setting needs no migration. `000002_seed_initial_data` seeds the current keys.

**`challenges`**: design challenges ([api.md](api.md#profiles-leaderboards-challenges)). `id` short id, `slug` unique (the public name in URLs), `title` (1-120), `summary` (<= 300), `description` (Markdown, <= 10000), `icons`, `rules` jsonb (`challenge.Rules`: content, kind, goal, restrictions, optional imports; any game version; validated by `internal/challenge`), `starts_at` < `ends_at` <= `voting_ends_at`, `require_new_revisions`, `voters_before_start`, `voting_enabled`, `votes_per_user` (1-20), `live_leaderboard`, `hidden_until_start` (not listed or found before `starts_at`), `published_at` (null: draft), `awarded_at` (when the closed challenge's XP awards went out, once, by the `challenge_awards` task), `created_at`, `updated_at`. Status (draft, upcoming, open, judging, closed) is derived from the times. No stored scores: submissions are checked when read.

**`challenge_submissions`**: `id`, `challenge_id`, `entry_id`, `user_id` (all cascade), `submitted_at`, `withdrawn_at` + `withdrawn_reason` (`replaced|user|unlisted`), `staff_verdict` (`accepted|rejected`, null: the rule check decides) and `staff_reason`. Partial unique indexes: one active submission per user and per entry in a challenge. The trigger `entries_withdraw_challenge_entry` (after any update of an entry that is not listed afterwards, `withdraw_unlisted_challenge_entry()`) withdraws its active submissions to challenges not yet ended, so leaving public, a delete, the expiry sweep or an account deletion all take it out, for good.

**`challenge_votes`**: pk `(challenge_id, user_id, entry_id)` (cascade), `created_at`, `voided_at`/`void_reason` (staff voided it: it stops counting but the row stays, so the voter cannot take it back and give it again). At most `votes_per_user` on active submissions per user and challenge, checked by the API under the voter's row lock; never on one's own entry.

**`board_leaders`**: the current leader of each leaderboard board ([api](api.md#profiles-leaderboards-challenges)), written every minute by the `leaderboards` task and read whole by every card listing for the record chips. `board` pk (`fastest|thrust_to_weight|lightest|most_cargo|most_science|densest_science|cleanest_science|biggest_power_plant`), `entry_id` and `blueprint_id` (cascade), `user_id` (the entry's owner, null when anonymous; set null with the account), `value`, `since` (moves only when another entry takes the lead). No history; a board with fewer than 10 ranked entries has no row. The candidates come from `blueprint_stats`, through the partial index `idx_blueprint_stats_board_candidates` (a complete analysis of a space platform, of a build with a `-science-pack` product or intermediate, or with positive net electricity; `ListBoardCandidates` repeats the predicate word for word).

**`xp_events`**: the append-only XP ledger ([architecture](architecture.md#leaderboards-xp-and-badges)). `id`, `user_id` (cascade with the account), `reason` (`upload|favorite|collection|comment|record|challenge_win|challenge_second|challenge_third|challenge_participation`), `points` (> 0), `source_key` (unique: the event that earned it, e.g. `upload:<entry>`, `favorite:<user>:<entry>`, `record:<board>:<entry>`, `challenge:<id>:place:<user>`), `entry_id`, `comment_id`, `challenge_id`, `board` (no foreign keys: a hard-deleted entry's row just stops counting), `created_at`. Never updated. A row counts towards a total while its entry is live and its comment not removed; the daily caps count every row of the UTC day per user and reason. Indexed `(user_id, reason, created_at)`.

**`home_picks`**: the home page's hand-picked leaves ([admin](admin.md#home-picks)): `blueprint_id` pk (cascade), `caption` (one line, <= 140, empty for none), `picked_at`, `picked_by` (console username). At most 6 (the staff operation, under an advisory lock). Shown only while the leaf is in the current revision of a listed entry.

**`admin_actions`**: the staff audit log. `id`, `staff_username` (the console's sign-in email; staff are not expo accounts), `action`, `target_type`, `target_id` (an id, never personal data), `reason`, `before`/`after` (jsonb, the changed fields), `created_at`. One row per staff write, written in the same transaction as the change; read newest first by `(created_at, id)`. Staff-only ([admin.md](admin.md)).

## Tree shape

`revisions.tree` holds typed pointers only; label, description, icons and
strings live in the rows.

```json
{ "kind": "book", "id": "<id>", "children": [
    { "kind": "book", "id": "<id>", "children": [ { "kind": "blueprint", "id": "<id>" } ] },
    { "kind": "upgrade_planner", "id": "<id>" },
    { "kind": "blueprint", "id": "<id>" } ] }
```

A single-blueprint entry is just `{ "kind": "blueprint", "id": "..." }`; a
single planner `{ "kind": "deconstruction_planner", "id": "..." }`. Planner
kinds point into `planners`, `book` into `books`, `blueprint` into
`blueprints`. Child order is the `children` array order. Each row belongs to
exactly one revision. To render: read the tree, batch-fetch referenced ids from
the three tables, hydrate.

## Anonymous editing

Anonymous creates get a random edit token (256 bits, shown once); it is the
only way to edit, revise or delete while ownerless. Only its SHA-256
(`edit_token_hash`) is stored, so a database dump or backup grants no edit
rights. Claiming is publishing: a signed-in user
presents the token to `POST /api/v1/entries/{id}/publish`, which sets
`owner_user_id` and clears the token ([api.md](api.md)).

## Deferred (no schema change needed to add)

a blob-storage key/checksum/size on `blueprints` once object storage exists.
